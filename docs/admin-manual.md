# Eidolon-SC 管理者操作手册

> **适用对象**：已经按 [`deploy.md`](deploy.md) 用 `docker-compose.prod.yml` 把 Eidolon-SC 部署到 Linux 服务器的部署者，以及 `.env` 的 `EIDOLON_ADMINS` 里列出的管理者。
>
> **这份手册解决什么**：不登录服务器，怎样在后台改模型、key、限额和开关；怎样看用量、花费和服务状态；怎样封禁、限额、删除用户；怎样发公告、发邀请、做备份；以及后台进不去时怎样用命令行兜底。
>
> **配套文档**：[部署指南](deploy.md)、[配置指南](configuration.md)、[`.env.example`](../.env.example)、[术语表](../GLOSSARY.md)。
>
> 本手册按当前仓库代码整理。页面文案或行为以后有改动时，以实际页面为准。

## 0. 一页纸速查

| 你要做的事 | 去哪里 | 备注 |
|---|---|---|
| 进后台 | `https://你的域名/admin` | 也可以在「设置 → 登录与数据」里点「进入后台」 |
| 改模型、key、限额、玩法开关 | `/admin/config` | 保存即生效，不用重启；进行中的通话按接通时的配置走完 |
| 看用量、花费、服务健康、备份 | `/admin` | 默认页；分「概览 / 用量 / 好感度 / 花费」 |
| 找用户、封禁、单独限额、增加抽奖次数、删除 | `/admin/users` | 搜索名字、邮箱或用户 ID |
| 写公告、置顶、撤回 | `/admin/announcements` | 发布后出现在用户对话列表的铃铛里 |
| 发邀请链接 | `/admin/config?tab=registration` | 只在「只让受邀的人注册」时有意义 |
| 立即备份 | `/admin` 的「备份」卡 | 需要先在 `.env` 配好备份 |
| 加/减管理员 | 服务器上的 `.env` | 后台不能改名单；改完 `up -d` |

**三句话记住后台的机制**：

1. **后台就是同一个网站上的 `/admin`**，不是另开的服务。只有管理者能进，其他人访问会得到 404，和这个地址不存在一样。
2. **后台改的配置存在数据库里，优先于 `.env`**。`.env` 是默认值和保底；后台改过之后，再改 `.env` 里的同一项不会生效，要先在后台「恢复成 `.env` 的值」。
3. **用户管理只有五件事**：看用量、封禁/解封、单独限额、增加抽奖次数、删除。后台看不到任何人的对话、记忆、制作人档案、好感度和礼物；抽奖次数可以增加，但看不到现有余额。

## 1. 后台是什么，凭什么能管

### 1.1 它不是一个独立系统

后台是网站的一部分：

- 页面在 `https://你的域名/admin`，和用户用的是同一个前端、同一个后端、同一个数据库。
- 后台接口在 `/api/admin/...`，对非管理者一律返回 **404**，不返回 401/403，避免暴露「这里有个后台」。
- 后台没有单独的密码。管理者用自己平时的 Google / GitHub 账号登录，后端根据登录身份判断是不是管理者。
- 后台的改动写进 SQLite 的 `config_overrides` 表，随每天的加密备份一起走。

### 1.2 谁能进后台

管理者的认定只看 `.env` 里的一行：

```sh
EIDOLON_ADMINS=github:12345,google:109876543210
```

规则：

- 每一项是 **`提供方:身份标识`**，提供方只能是 `github` 或 `google`。
- **按登录身份认定，不按邮箱**。两个人用同一个邮箱，也是两个用户。
- 一位用户绑定了多种登录方式时，**只要有一种在名单里**，他就是管理者。
- 名单只能在服务器上的 `.env` 里改，后台里不能增减。
- 所有管理者权限完全一样，没有角色分级。
- 后台**不能封禁或删除管理者**（包括自己）；命令行可以封禁管理者，但没有删除管理者的命令。
- 后台**没有操作审计日志**。多位管理者时，建议自己约定变更记录（谁在什么时候改了什么）。

三种特殊情况：

| 情况 | 结果 |
|---|---|
| `EIDOLON_ADMINS` 为空，且没开开发登录 | **没有后台**，所有人访问 `/admin` 都是 404 |
| `EIDOLON_ADMINS` 为空，但开了 `EIDOLON_DEV_LOGIN=1` | 所有用户都是管理者（仅限本机开发；公网部署不要开） |
| 管理者被命令行封禁 | 仍然进不了后台（后台要求未封禁且已同意条款） |

### 1.3 配置的两层：`.env` 和后台覆盖

```text
.env 的值 ──默认──┐
                  ├──> 当前生效的值 ──> 之后的回合 / 通话 / 朗读 / 搭话 / 朋友圈 / 信
后台覆盖（数据库）──优先──┘
```

- **没有标注** = 这一项用的是 `.env` 的值。
- **蓝色「已被后台覆盖」** = 后台存了覆盖，当前生效的是覆盖值。
- **黄色「覆盖没有生效」** = 后台存了覆盖，但试调失败，当前回退到 `.env` 的值；覆盖本身还留着，等你修好或恢复。
- 配置页的每一项都可以「恢复成 `.env` 的值」，也就是删掉这一项的覆盖。
- key 只显示**末 4 位**，任何时候都看不到完整值。
- 没有设 `EIDOLON_SECRET_KEY` 时，key 不能加密存进数据库，**后台里的各种 key 只能看、不能改**；其他项照常可以改。

### 1.4 哪些能在后台改，哪些只能在服务器上改

**只能在 `.env` 里改、后台只显示的 8 类**（配置页「只读」标签）：

| 项 | 为什么不能在后台改 |
|---|---|
| 管理者名单 | 改错了会把自己锁在门外；被攻破的后台也能借此把别人加成管理者 |
| `EIDOLON_SECRET_KEY` | 后台保存的 key 用它加密，封禁名单也靠它；换了就都解不开、认不出 |
| OAuth 登录 | 登录靠它，改错了谁都进不了后台去修 |
| 域名 | 改了以后登录回调、Cookie 和 HTTPS 证书都要跟着变，需要重新部署 |
| WebRTC / TURN | 通话的连接方式由服务器和防火墙一起决定 |
| 备份 | 备份去哪、用什么加密，关系到数据能不能找回 |
| 路径 | 数据库和角色配置的位置，进程启动时就定了 |
| 向量化的服务和模型 | 换了要重新计算全部向量（`eidolon reembed`），不能在运行中切换 |

### 1.5 后台看不到什么

后台**看不到**任何一位用户的：

- 对话内容、角色发来的照片和照片描述；
- 角色记下的记忆；
- 制作人档案；
- 各位角色对他的好感度、冷却；
- 礼物、重置卡、抽奖次数、成就、日程、周期记录、光顾记录、朋友圈（动态、配图、赞和评论）、信。

不过可以在用户详情里给某位用户**增加**抽奖次数（见 5.5）；后台不会因此显示他现有的余额或礼物。

后台**能看到**的只有：

- 登录方式（Google / GitHub、显示名、邮箱）、注册时间、最后活跃时间；
- 经哪条邀请链接注册的（如果有）；
- 最近 24 小时 / 7 天 / 30 天的回合和通话次数，包括被限额拒绝的次数；
- 这些用量里有多少用的是用户自带的密钥；
- 是否被封禁、封禁备注、有没有单独限额。

> **注意**：这是后台界面和后台 API 的边界，不等于「服务器上绝对看不到」。有服务器 root 权限的人仍然可以直接读 SQLite 数据库和备份。管理者的纪律是：不因为「技术上能看」就去翻用户的对话。

## 2. 上线当天：把后台开起来

### 2.1 先确认 `.env` 里这四项

在服务器上的仓库根目录：

```sh
cd /path/to/eidolon-sc
nano .env
```

| 变量 | 怎么填 | 说明 |
|---|---|---|
| `EIDOLON_SECRET_KEY` | `openssl rand -hex 32` 生成 | **填了就不要再换**。它加密后台保存的 key，也给封禁名单做哈希。换了以后，后台里带 key 的覆盖会解不开并回退到 `.env`，封禁名单也会对不上 |
| `EIDOLON_ADMINS` | `github:12345,google:109876543210` | 先留空也可以；等第一次登录、查到标识后再填 |
| `EIDOLON_CONTACT` | 例如 `admin@example.com` | 可选。被封禁的用户登录时看到它，隐私政策末尾也显示它 |
| `EIDOLON_REGISTRATION` | `invite` 或 `open` | 可选。只给认识的人用时填 `invite`；不填是 `open` |

同时确认：

- 至少配了 GitHub 或 Google 的一家 OAuth；回调地址分别是 `https://你的域名/api/auth/github/callback` 和 `https://你的域名/api/auth/google/callback`。
- **不要**填 `EIDOLON_DEV_LOGIN`。配置了 `EIDOLON_DOMAIN` 的公开部署检测到它会拒绝启动。

### 2.2 第一次登录，查到自己的标识

1. 打开 `https://你的域名`，用你自己的 Google 或 GitHub 登录。
2. 第一次登录要同意隐私政策和使用条款、声明年满 13 岁。
3. 在服务器上列出用户：

   ```sh
   docker compose -f docker-compose.prod.yml exec backend eidolon user list
   ```

   输出里每位用户的登录方式后面括号里就是标识，例如：

   ```text
   github:12345
   google:109876543210
   ```

4. 把对应的一项或几项填进 `.env`：

   ```sh
   EIDOLON_ADMINS=github:12345,google:109876543210
   ```

> **不要填邮箱**。`github:` / `google:` 后面是数字身份标识，不是邮箱地址。

### 2.3 让后端读到新配置

```sh
docker compose -f docker-compose.prod.yml up -d
```

注意：

- 只 `restart` **不会**重新读 `.env`；要用 `up -d` 重建后端容器。
- `up -d` 会短暂中断服务，进行中的通话会被挂断。尽量在低峰期做。
- 启动日志里可以确认覆盖项：

  ```sh
  docker compose -f docker-compose.prod.yml logs backend | grep "config overrides"
  ```

### 2.4 进入后台

刷新页面，在「设置 → 登录与数据」里应该出现「后台」一节，点「进入后台」；或者直接打开：

```text
https://你的域名/admin
```

看到「看板」就说明开通成功。看不到入口、访问 404 时，先查「9. 故障排查」。

### 2.5 开通后的第一轮检查

按顺序做完这 8 件事，再对外发网址：

| # | 检查 | 怎么做 | 通过标准 |
|---|---|---|---|
| 1 | 备份正常 | 看板「备份」卡 →「立即备份」 | 状态正常，显示上一次成功的时间和大小 |
| 2 | 服务健康 | 看板「概览 → 服务健康」 | 各项正常；没有红色/黄色点 |
| 3 | 配置生效 | 随便打开「配置 → 模型」 | 能看到当前生效值；需要改的项没有黄色「覆盖没有生效」 |
| 4 | 限额合理 | 「配置 → 限额与玩法 → 限额」 | 回合/通话/照片/朗读/光顾符合你的预算 |
| 5 | 注册方式 | 「配置 → 注册」 | 只给认识的人用时是「只让受邀的人注册」 |
| 6 | 邀请链接 | 「配置 → 注册 → 邀请链接」 | 生成第一条，复制链接，自己打开能进登录页 |
| 7 | 公告 | `/admin/announcements` | 写一条欢迎/规则公告并发布 |
| 8 | 管理员账号安全 | 你的 Google / GitHub 账号 | 开了两步验证；不和别人共用 |

另外建议在服务器上跑一次 doctor，确认 `.env` 一侧没有错：

```sh
docker compose -f docker-compose.prod.yml run --rm backend eidolon doctor
```

doctor **只查 `.env`**，不查后台覆盖。后台改过的项不在它的检查范围里。

## 3. 看板：每天五分钟看什么

### 3.1 时间范围和刷新

- 范围：**24 小时 / 7 天 / 30 天 / 90 天**。运行记录只保留 90 天，所以 90 天是上限。
- 页面看得见时每分钟自动刷新一次；页首会写「数据截至 16:25」。
- 切换范围或手动刷新时，新数字到之前旧数字会变淡，避免把上一个范围的数字当成这个范围的。
- 范围和分组记在地址里，可以收藏，例如：

  ```text
  /admin?range=7d&tab=cost
  /admin?range=30d&tab=usage
  ```

### 3.2 「概览」看什么

| 卡片 | 内容 | 怎么看 |
|---|---|---|
| 回合 | 范围内成功/失败/被拒绝/用户离开的回合数 | 失败和被拒绝突然变多，先看「服务健康」 |
| 通话 | 通话数、其中不计入限额的次数 | 不计入限额多，说明自带密钥的用户多 |
| 活跃用户 | 范围内有回合或通话的用户数 | 和趋势一起看，判断是「人少了」还是「每个人用得少了」 |
| 进行中的通话 | 此刻正在通话的数量（每分钟刷新） | 接近 `concurrent_calls` 上限时，新通话会 503 |
| 用自带密钥的回合 | 数量和占比 | 占比高说明部署者负担轻 |
| 到开口（中位数） | 从用户说完到她开始回复的中位时间 | 变慢时看 LLM 延迟和首字延迟 |
| 服务健康 | 各项服务的调用、出错率、延迟 | 见 3.6 |
| 备份 | 上一次成功、存储桶份数、保留期、失败原因 | 见 3.7 |

### 3.3 「用量」看什么

- **回合趋势 / 通话趋势**：按小时、6 小时、天分桶；点上看具体数字。
- **回合结果**：成功、失败、被拒绝、用户离开。
- **通话结果**：成功、因故障中断、被拒绝、没能接通。
- **通话时长**：中位数、九成在多少以内。
- **结束原因**：用户挂断、离开对话页、撞上时长上限、撞上回合上限、角色挂断、被封禁、用户被删除、故障、服务重启或关闭。
- **按角色**：每位角色的回合数、通话数；已下线角色会单独列出。
- **搭话**：搭了几次、失败几次、被回的占比。
- **信**：写了好几封、失败几次。
- **酒吧**：光顾几次、玩完几次、失败几次。
- **朋友圈**：发了几条、发失败几次、回评论几次、回失败几次、近 30 天制作人赞或评论过的占比。

### 3.4 「好感度」看什么

只有好感度和礼物开着，或范围内有成就、日程、周期数据时，这个标签才出现。

- **打分分布**：0（伤害了她）到 4（让她很开心）各占多少。
- **不该说的话 / 操纵**：命中次数。
- **进入冷却**：次数和涉及的用户数。
- **按角色**：判断过的回合、加分占比、减分占比、冷却次数、她挂断或结束对话的次数。
- **日程 / 周期 / 成就**：本周排了日程的人数、记过周期的用户数、解锁的成就阶段和因此发出的抽奖次数、重置卡。

这里只有**全站合计**，看不到某位用户的好感度。管理者也不能调整任何人的好感度。

### 3.5 「花费」看什么

- 只估算**部署者的 key** 花的钱；用户自带密钥的调用只列用量，不算钱。
- 按币种分别汇总（USD / CNY），**不互相换算**。
- **合计（估算）**、**花费趋势**、**按服务**、**按模型**、**计费用量**、**单价**、**未设单价**。
- 有调用没说用量时，会单独写「另有 N 次调用没说用量，没有算进去」。
- 目录价格更新时间和预设整理时间会写在页首提示里。

### 3.6 服务健康

看板按统计时段里**部署者 key** 的调用计算每项服务的状态：

| 状态 | 判定 | 你要做什么 |
|---|---|---|
| 正常 | 出错率低于 5% | 不用管 |
| 出错偏多 | 5%～50% | 看错误类别；如果是 key/余额，去改配置 |
| 大量出错 | 50% 以上 | 优先处理；必要时先降级或换服务 |
| 没有调用 | 时段内没有调用 | 后台会用最小请求试一下；生图不试 |

错误类别：超时、连不上、限流、密钥或余额、请求被拒、服务端出错、返回无法解析、其他。

空闲服务的试调：

- 每项服务每个时段最多试两次，花费几乎为零；
- 试的这一下不进运行记录，也不算看板的用量和花费；
- 生图每张都花钱，**不试**，没有调用时显示「最近没有调用」；
- 语音合成和识别要等通话结束才写进运行记录，所以正在打的电话要到挂断后才反映到状态上。

### 3.7 备份

看板「概览」下面有「备份」卡，每分钟刷新：

- 上一次成功的时间、大小、发起者（每天的 cron / 服务器上手动 / 后台按钮）；
- 存储桶里的份数和总量；
- 保留期、空间提醒；
- 最近一次失败的原因（导出、上传、清理过期备份、配置不全、没有完成）。

异常判定：

| 显示 | 含义 | 动作 |
|---|---|---|
| 正常 | 最近一次成功，且没过期 | 不用管 |
| 备份中… | 有备份正在进行（不管是谁发起的） | 等；按钮会禁用 |
| 未配置 | `.env` 里备份设置一项都没填 | 按 [`deploy.md`](deploy.md)「备份」配置 |
| 配置有误 | 缺项或格式不对 | 按日志/页面提示补 `.env`，`up -d` |
| 还没有成功过一次 | 从没成功 | 先手动跑一次 `deploy/db-backup.sh` 看日志 |
| 超过 26 小时没有成功的备份 | cron 可能停了 | 检查 cron、服务器、存储桶权限 |

后台「立即备份」：

- 在后端进程里跑一次和 cron 一样的备份，不卡正在进行的通话；
- 输出在**后端日志**里（`docker compose ... logs backend`，以 `INFO: backup:` / `WARNING: backup:` 开头），**不在** `logs/db-backup.log`；
- 这次备份同样占锁；cron 撞上会以退出码 6 放弃；
- 后端在备份中途重启，这次会记成「没有完成」。

### 3.8 每天五分钟检查表

| 顺序 | 看什么 | 异常时 |
|---|---|---|
| 1 | 概览：服务健康有没有红/黄点 | 看错误类别，处理 key/余额/网络 |
| 2 | 概览：进行中的通话是否接近上限 | 调整 `concurrent_calls` 或排查异常长通话 |
| 3 | 概览：备份是否正常 | 点「立即备份」；看后端日志和 `logs/db-backup.log` |
| 4 | 花费：今天/本周的估算是否异常 | 按模型/服务找突增；看是不是有人刷量 |
| 5 | 用量：失败、被拒绝、结束原因是否异常 | 结合服务健康判断是故障还是限额 |
| 6 | 用户：按 24 小时回合/通话排序，看有没有异常用户 | 单独限额或封禁，见第 5 节 |
| 7 | 公告：有没有需要通知的维护/变更 | 写公告，见 6.2 |

## 4. 配置：11 个标签逐项说明

打开 `/admin/config`。页首的说明是：

> 这里改的配置存进数据库，优先于 `.env`。LLM、语音、生图和判断模型保存前会先试调一次，试不通不保存；保存后新的回合和新的通话立刻用上，进行中的通话不受影响，不用重启。没有标注状态的项用的是 `.env` 的值。

### 4.1 通用规则

**状态**

| 状态 | 含义 | 你要做什么 |
|---|---|---|
| 没有标注 | 用 `.env` 的值 | 正常 |
| 蓝色「已被后台覆盖」 | 当前生效的是后台存的值 | 想回 `.env` 就点「恢复成 `.env` 的值」 |
| 黄色「覆盖没有生效」 | 后台存了值，但试调失败，回退到 `.env` | 看原因，修好或恢复 |

标签上出现黄色点，说明这个标签里有覆盖没生效，不必逐张卡找。

**保存**

- 服务类（LLM、TTS、STT、生图、GPT Image、判断模型、和风天气、网络代理）：按钮是「试调并保存」。后端会先按新值真连一次；失败就不保存，并显示服务返回的原话。
- 阈值、限额、开关类：按钮是「保存」，只做范围检查，不试调。
- key 留空 = 不改。要换 key 才填新的。
- 保存成功后，**新的回合、新的通话**用新值；进行中的通话按接通时的语音合成、语音识别、情绪判断模型和通话上限走完。检索判断、重排阈值、历史回合数这类按回合读取的项，会在通话的下一个回合生效。

**恢复**

- 配置项的卡底部有「恢复成 `.env` 的值」。
- 「赞赏」「邀请链接」「单价」不是 `.env` 里的项，没有这个按钮；它们各有自己的删除/清除操作。

**只读**

- 「只读」标签列出 8 类只能看、不能改的项；key 只显示「已设置 / 未设置」。

### 4.2 「模型」标签

| 卡片 | 你可以改 | 保存前会做什么 | 生效范围 | 运维要点 |
|---|---|---|---|---|
| 扮演角色的 LLM | 接口协议、地址、模型名、`max_tokens`、文字的思考强度、通话的思考强度、额外请求参数、API key | 用同样的检查试调：必须支持流式输出和工具调用 | 之后的文字回合和通话 | 换模型先小流量观察；`extra_body` 不能含 `model`、`stream`、`messages`、`tools` 等保留字段；思考强度和 `extra_body` 不要同时设 |
| 后台模型 | 同样的字段，但没有「通话的思考强度」 | 同上 | 之后提炼记忆、给对话起标题 | 不填的项跟随对话模型；`max_tokens`、思考强度、额外请求参数始终独立 |
| 判断模型 | 服务（Jev / Cloudflare / 阿里云百炼）、模型名、Cloudflare 账号 ID、百炼业务空间 ID、地域、情绪判断超时、key | Cloudflare 和百炼做启动时的检查；Jev 问一个最小的问题 | 之后的回合和通话中的情绪判断 | 换判断模型时，判断阈值的覆盖会被清掉；Cloudflare 只能是 `clef` 或 `clef-flash`，百炼填 `decision-model-preview` |
| 判断模型的阈值 | 回忆阈值、情绪最低概率、「不该说的话」阈值、「操纵」阈值、「要照片」阈值 | 只查 0～1 | 之后的判断 | 阈值只对设置时选用的判断模型 family 生效；换了 family 就失效，后台会标出来 |
| 重排的阈值 | 剧情和角色资料的最低相关度、记忆的最低相关度 | 只查 0～1 | 之后的检索 | 阈值针对设置时的重排模型；在 `.env` 里换重排模型后，覆盖保留但不生效 |

**模型选择的小技巧**：

- 服务商和模型有下拉；选了服务商会自动填协议和地址，选了模型会填模型名。也可以手填。
- 对话模型和后台模型可以「向服务商查这把 key 能用的模型」，查到的会替换本地目录里的列表。
- 换供应商时，先确认 `base_url` 填到哪一级：OpenAI 兼容一般到 `/v1`，Anthropic 和 OpenAI Responses 按服务商文档。

### 4.8 「限额与玩法」标签

#### 4.8.1 限额、单次通话上限和历史回合数

| 字段 | 默认 | 填 0 / 选「不限」 | 说明 |
|---|---|---|---|
| 每小时回合数 | 60 | 不限 | 每位用户分别计算；用自带 LLM 的文字回合不计入 |
| 每小时通话次数 | 5 | 不限 | 每位用户分别计算；通话带齐免限额密钥才不计入 |
| 每小时照片数 | 5 | 不限 | 文字回合和通话共用；用自带生图的不计入 |
| 每小时光顾次数 | 5 | 不限 | 用自带 LLM 的光顾不计入 |
| 每小时朗读次数 | 60 | 不限 | 用自带语音合成 key 的朗读不计入 |
| 单次通话时长上限（分钟） | 10 | 不限 | 对所有人都一样，不能给某位用户单独设 |
| 单次通话回合上限 | 40 | 不限 | 同上 |
| 同时进行的通话数上限 | 10 | 不限 | 全站合计，免限额通话也算；满了新通话 503 |
| 带上的历史回合数 | 20 | — | 每个回合至少读最近这么多回合；太小接不上，太大增加费用 |

**免限额密钥**三个开关：

- `免限额密钥：LLM`、`免限额密钥：语音合成`、`免限额密钥：语音识别`。
- 打开的项目，用户必须**自带**这一项，通话才可能不计入限额；没打开的项目由部署者承担，带不带都不影响计数。
- 至少开一项；最后一项关不掉。想彻底取消限额，把每小时的回合数和通话次数设成「不限」。
- 文字回合和光顾不看这三个开关：用了自带 LLM 就不计入。
- 生图不能选进免限额密钥。

**怎么算**：

- 按用户合并，不论用哪种登录方式、在哪台设备。
- 因服务出错而失败的回合、没接通的通话不计入；用户自己中途离开的照常计入。
- 照片只看花的是谁的钱：没发出来的不计入，用自带生图的不计入，用了自带 LLM、照片却用部署者生图的照样计入。
- 光顾进门就算一次，重试不再算；第一次调用一句没写出来就失败的不计入。
- 朗读每点一次算一次：用自带语音合成的不计入，没合成出来的不计入。
- 超额返回 429，带恢复时间；同时通话满了返回 503。

#### 4.8.2 玩法开关

| 卡片 | 可改 | 生效 | 关掉时 | 默认 |
|---|---|---|---|---|
| 好感度和礼物 | 开关；给所有现有用户各发一张重置卡 | 从下一个回合起 | 不判断、不显示，冷却也不拦人；已有好感度原样保留 | 开（需要判断模型；没配判断模型时整块关闭，后台也打不开） |
| 搭话 | 开关、每位用户每天最多几次 | 下一分钟起 | 不再主动搭话；已发出的不受影响 | 关 |
| 信 | 开关 | 下一分钟起 | 不再写新信；已经写好的照样能看 | 关 |
| 朋友圈 | 开关、每天最多几条、地图（OSM / Google / 高德）、每天最多回几条评论 | 下一分钟起 | 只是不发、不显示；已有动态照常到期删除 | 关 |
| 日程 | 开关 | 下一次读取起 | 日历只有月视图；角色不再提起日程；已排的原样保留 | 开 |
| 周期 | 开关 | 下个回合 / 下次搭话起 | 她的言行、判断、挂断、礼物和对话事件都不受周期影响；周期本身照常在走 | 开 |
| 酒吧 | 开关 | 下一次进门起 | 进不了门；进行中的光顾照常走完 | 开 |

**好感度和礼物的「重置卡」**：

- 判断模型误判了一阵子时，用它给**所有现有用户**各发一张重置卡，作为整体补偿。
- 不能单独给某一位发；发出后不能收回。
- 之后注册的用户拿不到。
- 好感度和礼物关着时不能发。
- 发完可以顺手写一条公告（页面会链接到公告页）。

**给某位用户增加抽奖次数**不在配置页，在用户详情页：见 5.5。

### 4.9 「注册」标签

| 卡片 | 你可以改 | 生效 | 说明 |
|---|---|---|---|
| 注册方式 | 谁都能注册 / 只让受邀的人注册 | 立刻 | 后台改的优先于 `.env` |
| 邀请链接 | 备注、可用次数、有效期；复制、删除 | 立刻 | 只在「只让受邀的人注册」时起作用 |

**邀请链接规则**：

- 每条可用 **1～100 次**，没有「不限次」。
- 有效期：1 天、7 天、30 天、不过期。
- 备注只有管理者看得到，最多 100 字（比如发给谁）。
- 链接形如 `https://你的域名/login?invite=...`；对方打开后登录就注册好了。
- 每注册一位用户用掉一次；用户后来被删除，次数也不退。
- 删掉链接立刻失效；经它注册的用户照常使用。
- 列表里能看到每条链接已用几次、到期时间、经它注册了谁。

**谁不用邀请**：

- 已经注册过的用户照常登录；
- 绑定另一种登录方式不算注册；
- 管理者名单里的身份；
- 还一个用户都没有时，第一个登录的人（部署者自己先登录，才能查到标识）。

**被挡下的人**：回到登录页，提示向部署者要邀请链接；填了 `EIDOLON_CONTACT` 时附上联系方式。系统不建用户，也不留下他的任何信息。

### 4.10 「赞赏」标签

| 你可以做 | 说明 |
|---|---|
| 开关「在设置里显示」 | 打开后，用户在「设置 → 关于」上面看到「赞赏」 |
| 上传 / 换一张收款码 | PNG、JPEG 或 WebP，不超过 2 MB |
| 清除 | 开关会关掉，收款码会删除，用户不再看到「赞赏」 |

这不是 `.env` 里的配置，没有「恢复成 `.env` 的值」，只有「清除」。开着但还没传图时，用户看不到；页面会提示。

### 4.11 「单价」标签

看板按这里的单价估算部署者的花费。

- 单价以「**提供方 + 模型 + 计费单位**」为准；提供方是服务地址的主机名。
- 生效顺序：**后台设定 > 在线目录（models.dev 和 OpenRouter，每天更新，只有按 tokens 计费的模型）> 预设**。
- 服务地址不在目录里（例如中转）时，按模型名用原厂价格估算。
- 可以新增、修改、删除单价；可以「恢复成目录价格」或「恢复成预设」。
- 改了单价，**之前的花费也按新单价重新估算**。
- 页面列出预设、后台设定过的和最近 90 天用过的模型；用过但哪儿都找不到单价的模型会单独列出，看板上显示「未设单价」。
- 目录拉取失败时，页首会显示原因，可以点「立即从目录刷新」重试。

### 4.12 「只读」标签

这里只显示、不能改：

- 管理者名单、`EIDOLON_SECRET_KEY`、OAuth 登录、域名、WebRTC / TURN、备份、路径、向量化的服务和模型。

理由见 1.4。要改这些，只能上服务器改 `.env`，然后 `up -d`。

## 5. 用户管理

打开 `/admin/users`。

### 5.1 列表

- 搜索：名字、邮箱、用户 ID。
- 排序：最近注册、24 小时回合最多、24 小时通话最多。
- 每页 50 位；分页在底部。
- 一行显示：用户（登录方式在副行）、24 小时回合、24 小时通话、最后活跃、状态（正常/已封禁/管理者/单独限额）、操作（封禁/解除封禁）。
- 管理者那一行**没有封禁按钮**。

### 5.2 用户详情

点名字进入 `/admin/users/{id}`：

| 区块 | 内容 |
|---|---|
| 资料 | 登录方式（Google / GitHub、显示名、邮箱）、标识、用户 ID、注册时间、最后活跃 |
| 邀请 | 如果经邀请链接注册，显示那条链接的备注 |
| 封禁 | 封禁时间、封禁备注（只有管理者看得到） |
| 近期用量 | 最近 24 小时 / 7 天 / 30 天的回合、通话、被拒绝；每项再分「部署者」和「自带密钥」 |
| 单独限额 | 当前是否单独设了限额；可以修改或取消 |
| 操作 | 封禁 / 解除封禁、增加抽奖次数、删除这位用户 |

用量说明：

- 回合包括通话里的回合；
- 被拒绝的回合和通话（多是撞上限额）只计入「被拒绝」；
- 通话那一行的「不计入」指带齐免限额密钥、不计入限额的通话。

### 5.3 封禁与解封

**封禁**：

1. 点「封禁」，填写备注（只有管理者看得到，最多 500 字）。
2. 确认后：
   - 用户在所有设备上退出登录；
   - 进行中的通话在几秒内挂断；
   - 用户不能再登录；
   - 数据保持原样。
3. 被封禁的用户登录时看到「已被封禁」；填了 `EIDOLON_CONTACT` 时会附上联系方式。

**解除封禁**：

- 点「解除封禁」，用户可以重新登录。
- 封禁备注同时清除。

**注意**：

- 后台不能封禁管理者（包括自己）；命令行可以。
- 封禁不是删除；数据还在，随时可以解封。

### 5.4 单独限额

点「设定单独限额」或「修改单独限额」：

| 项目 | 可选 |
|---|---|
| 每小时的回合数 | 跟随全站 / 设定次数 / 不限 / 只能用自带密钥 |
| 每小时的通话次数 | 同上 |
| 每小时的照片数 | 同上 |
| 每小时的光顾次数 | 同上 |
| 每小时的朗读次数 | 同上 |

规则：

- 「跟随全站」= 用配置页「限额」里的数字。
- 「设定次数」= 只对这位用户生效。
- 「不限」= 这位用户不受这一项限制。
- **「只能用自带密钥」** = 只放行不计入限额的请求：
  - 回合：只放行用自带 LLM 的文字回合；
  - 通话：只放行带齐当前免限额密钥的通话；
  - 照片：只发用自带生图生成的照片；
  - 光顾：只放行用自带 LLM 的光顾；
  - 朗读：只用自带语音合成的 key 朗读。
- 至少要单独设定一项；都跟随全站的话，用「取消单独限额」。
- 保存后从这位用户的下一个回合、下一次通话、光顾或朗读起生效。
- **单次通话的时长和回合上限对所有人都一样，不能单独设。**
- 备注只有管理者看得到。

### 5.5 增加抽奖次数（补偿）

在用户详情底部点「增加抽奖次数」：

1. 填要增加的次数，1 到 1000 次；只用于补偿，不是常规运营手段。
2. 确认后，次数直接加在这位用户现有的抽奖次数上；**可以超过每天最多攒的 7 次上限**，和成就给的一样不受上限约束。
3. 用户下次打开礼物页会看到新到的次数，礼物页和玩法图标上会出现「新到的抽奖次数」的点。
4. 好感度和礼物关着时不能增加，会提示「礼物暂时没有开放」。
5. 后台**不会显示**用户现在有多少次抽奖，也看不到他的礼物；增加的次数是加在现有余额上的，不是把余额设成这个数字。

限制：

- 只能加抽奖次数，不能加礼物，也不能单独发重置卡（重置卡只能在配置页「好感度和礼物」里给所有现有用户各发一张）。
- 这个操作没有单独的审计记录；需要留痕的话，自己记下时间、用户和次数。
- 增加后不能撤回。给错人时只能再走数据库修（见第 10 节的风险说明），所以确认前看清用户。

### 5.6 删除用户

删除和用户自己点「删除我的全部数据」完全一样：

- 彻底删除记忆、对话、制作人档案、登录方式、登录状态和限额计数；无法恢复。
- 进行中的通话随即挂断。
- 每天的加密备份里的副本最多再留 30 天。
- 删除后，如果用户没被封禁，他再用同一种登录方式登录，会是**一位全新的用户**。
- 如果用户**已被封禁**：删除后，他用过的登录方式仍然不能再登录，也不能被绑定；**删除不等于解封**。

确认框会再列一遍后果。删除管理者会被拒绝。

### 5.7 封禁还是删除：怎么选

| 情况 | 建议 | 理由 |
|---|---|---|
| 刷量、滥用，但可能只是一时 | **先单独限额**，再观察 | 立刻生效，可逆 |
| 明确违规，想让他不能再登录 | **封禁** | 数据保留，可解封 |
| 明确违规，且不想让他换设备再来 | **封禁 → 再删除** | 删除后同身份也不能再注册；但不可逆 |
| 用户自己要求删号 | **删除** | 和用户自己删一样；先提醒备份/导出 |
| 误封 | **解除封禁** | 备注清除，数据还在 |

> **重要**：封禁后删除，会把他的登录身份做成哈希存进封禁名单，**永远不会过期**，也没法再对应回人。所以「封禁后删除」不能反悔。如果只是想让对方冷静一下，用封禁或单独限额。

### 5.8 命令行兜底

后台进不去，或想批量处理时：

```sh
# 用户列表：ID、名字、登录方式（括号里是 EIDOLON_ADMINS 的标识）、创建时间、是否封禁
docker compose -f docker-compose.prod.yml exec backend eidolon user list

# 封禁，并让他在所有设备上退出登录
docker compose -f docker-compose.prod.yml exec backend eidolon user ban <用户 ID> --note "刷量"

# 解除封禁
docker compose -f docker-compose.prod.yml exec backend eidolon user unban <用户 ID>

# 最近 24 小时按小时的用量；7 天、30 天在后台用户详情里看
docker compose -f docker-compose.prod.yml exec backend eidolon user usage <用户 ID>
```

命令行没有删除用户的命令；删除只能在后台或由用户自己操作。

## 6. 日常沟通：邀请、公告、赞赏、补偿

### 6.1 开邀请制

**什么时候用**：只给认识的人用，不想让找到网址的陌生人注册、花你的钱。

**步骤**：

1. `配置 → 注册 → 注册方式`，选「只让受邀的人注册」，保存。
2. 点「生成邀请链接」：
   - 备注：写给谁，只有你看得到；
   - 可用次数：1～100；
   - 有效期：1 天 / 7 天 / 30 天 / 不过期。
3. 生成后点「复制链接」，发给对方。
4. 对方打开链接，用 Google 或 GitHub 登录，就注册好了；以后直接登录，不再需要链接。
5. 在列表里看「已用 N / M 次」和「经它注册」的人。

**链接泄露时**：

- 删掉链接，立刻失效；
- 到「用户」里找到经它注册的人，按 5.7 处理。

**从开放改邀请制**：已经注册的人照常使用，不用重来。要清掉陌生人，用封禁或删除。

**从邀请改开放**：`注册方式` 改成「谁都能注册」，保存即可。邀请链接还可以留着，但不再是必需的。

### 6.2 发公告

打开 `/admin/announcements`。

**写一条**：

1. 点「写公告」。
2. 填正文，最多 5000 字。
3. 支持 Markdown 的**加粗、斜体、链接、列表、行内代码**；换行照原样换行；**不支持标题、图片和 HTML**。
4. 可以「预览」。
5. 「保存草稿」或「发布」。

**发布后**：

- 出现在用户对话列表的**铃铛**里；有未读时铃铛有标记。
- 用户最多看到**置顶的一条 + 最近 20 条已发布**的公告。

**修改**：

- 已发布的公告可以改正文，**不会**让用户再看到一次未读。
- 想让用户重新看到，先「撤回」再「发布」；这算一条新公告。
- 撤回会同时取消置顶。

**置顶**：

- 只能置顶已发布的公告；同时只有一条置顶；置顶另一条会自动取消原来的。
- 置顶不会改变发布时间，也不会让它变成「新公告」。

**删除**：

- 删除后不能恢复；已发布的会从所有用户的公告里消失。

**适合发公告的场合**：

- 换模型 / 维护 / 服务中断；
- 限额或玩法调整；
- 邀请制、注册规则变化；
- 重置卡补偿；
- 隐私政策、使用条款变化。

### 6.3 赞赏

`配置 → 赞赏`：

1. 上传收款码（PNG/JPEG/WebP，≤2 MB）。
2. 打开「在设置里显示」。
3. 用户在「设置 → 关于」上面看到「赞赏」，点开是这张收款码。

- 换图直接「换一张」。
- 不想收就「清除」：开关关掉，图删除。

### 6.4 误判补偿：重置卡

判断模型误判了一阵子（比如把正常的话判成「不该说的话」，导致好感度下降或冷却）时：

1. `配置 → 限额与玩法 → 好感度和礼物`。
2. 「给所有现有用户各发一张重置卡」→「发放」。
3. 确认：现有的 N 位用户每人多一张；之后注册的拿不到；发出后不能收回。
4. 建议顺手写一条公告，说明补偿原因。

限制：

- 不能单独给某一位发；
- 好感度和礼物关着时不能发；
- 不能调整某位用户的好感度或礼物；抽奖次数可以在用户详情里单独增加（见 5.5），但那是另一种补偿，不是发重置卡。

## 7. 典型运维剧本

### S1. 换对话模型或供应商

**何时**：想换更便宜的模型、原供应商不稳定、要更好的工具调用/日语表现。

1. **准备**：新服务的 base_url、key、模型名；确认支持流式输出和工具调用。
2. **看现状**：看板「服务健康」和「花费」记下当前错误率和成本，方便对比。
3. **改配置**：`配置 → 模型 → 扮演角色的 LLM → 修改`。
   - 选服务商/模型，或手填协议、地址、模型名；
   - 填新 key；
   - 需要的话调 `max_tokens`、思考强度。
4. **保存**：点「试调并保存」。失败会显示服务原话；不改动原配置。
5. **验证**：自己发一条消息，确认能流式回复、能调用工具（比如让她回忆剧情）。
6. **观察**：看板「服务健康」看 30 分钟到 1 小时；看「到开口」延迟和错误率。
7. **回滚**：改回原来的值再保存，或点「恢复成 `.env` 的值」（如果 `.env` 里是旧的正确值）。

注意：

- 进行中的通话不受影响，新通话用新模型。
- 如果你同时换了判断模型，判断阈值的覆盖会失效；换重排模型则重排阈值失效。看后台有没有黄色标记。
- 改的是后台覆盖；`.env` 里的 `CHAT_LLM_*` 不会变。

### S2. key 失效、欠费、被吊销

**表现**：服务健康红/黄；回合失败；保存时试调报「密钥或余额」；后台某张卡出现「覆盖没有生效」。

1. 到服务商控制台确认 key 状态、余额、权限。
2. 生成新 key（很多控制台只显示一次，当场复制）。
3. `配置 → 对应卡片 → 修改`，只填新 key，其他值不动。
4. 「试调并保存」。
5. 如果保存失败：
   - 看服务返回的原话；
   - 如果是网络问题，检查「网络代理」；
   - 如果是余额，充值或换服务。
6. 如果重启后出现「覆盖没有生效」：后台会回退到 `.env` 的值；修好覆盖或点「恢复成 `.env` 的值」。

### S3. 控制成本

**先看钱花在哪**：

1. 看板「花费」：按服务、按模型、按时间范围。
2. 看「未设单价」：没单价的模型不会算进合计，先补单价才能看清。
3. 看「用量 → 按角色」：是不是某位角色/某个玩法特别贵。

**常用手段**：

| 手段 | 怎么做 | 影响 |
|---|---|---|
| 收紧限额 | `配置 → 限额与玩法 → 限额`，调低每小时回合/通话/照片/朗读/光顾 | 立刻减少调用；用户会看到 429 |
| 单独限额 | 用户详情 → 单独限额 | 只针对重度用户 |
| 换便宜模型 | `配置 → 模型` | 直接降单价；注意工具调用和日语质量 |
| 关玩法 | 关掉搭话、信、朋友圈、酒吧等 | 这些用部署者的模型/生图，关掉就不产生费用 |
| 关好感度 | 关掉好感度和礼物 | 少一道判断，省判断 token；但礼物/成就一起停 |
| 降生图并发 | `配置 → 生图 → 同时生成几张` | 降低瞬时费用和排队 |
| 免限额密钥 | 让用户自带 LLM/TTS/STT | 用户自己付费；至少保留一项免限额 |

**注意**：

- 配置页的全站限额里，0 = 不限，不要用 0 来表示「关闭」。单独限额里的 0 是「只能用自带密钥」，含义不同。
- 关玩法不会删除已有数据；再打开会接着用。
- 好感度和礼物关着时，日程里做完的工作当时不加好感度，再打开时一起补加；酒吧的光顾当时什么都不给，之后也不补。
- 生图、GPT Image 的保存检查各花一张的钱，但很小。

### S4. 有人刷量或滥用

**发现**：

1. `用户` 页按「24 小时回合最多」或「24 小时通话最多」排序。
2. 点进详情，看 24 小时 / 7 天 / 30 天的用量，以及「部署者 / 自带密钥」的拆分。
3. 看「被拒绝」次数：如果很多，说明限额已经在挡；如果成功次数也很高，说明限额太松。

**处置顺序**：

1. **先单独限额**（推荐）：
   - 比如每小时回合 10、通话 1，或「只能用自带密钥」；
   - 保存后从下一个回合生效，可逆。
2. **再考虑封禁**：
   - 填备注，写明原因和时间；
   - 用户所有设备退出，通话几秒内挂断。
3. **严重且不想再见到他**：
   - 封禁 → 删除；删除后同身份永久拒绝；
   - 这一步不可逆，先确认。
4. **公告**：如果影响面大，写一条规则公告。

**注意**：

- 后台没有操作审计日志；需要留证据的话，自己截图保存。
- 不能调整对方的好感度或礼物；抽奖次数可以在用户详情里增加（见 5.5），但那是补偿，不是处罚手段。
- 不要因为「他说了难听的话」就封禁；先看使用条款和你的规则。角色自己的冷却/挂断是玩法，不是封禁。

### S5. 开邀请制 / 关闭注册

**开邀请制**：

1. `配置 → 注册 → 注册方式` →「只让受邀的人注册」→ 保存。
2. 生成邀请链接，发给要邀请的人。
3. 观察「经它注册」列表；链接泄露就删。

**关闭注册（只留现有用户）**：

- 同上，保持「只让受邀的人注册」，但不发新链接。
- 已有链接可以全部删掉，立刻失效。
- 已经注册的用户照常登录。

**重新开放**：

- 改成「谁都能注册」，保存。
- 考虑先发公告说明规则。

### S6. 发维护/变更公告

1. `/admin/announcements` →「写公告」。
2. 写清楚：什么时候、影响什么、用户要做什么。
3. 预览 → 发布。
4. 重要的公告「置顶」。
5. 维护结束后可以撤回或再发一条「已恢复」。

### S7. 备份与恢复

**日常**：

- 看板「备份」卡每天看一眼；
- 确认 cron 在跑（`crontab -l`）；
- 确认存储桶是**私有**的，和立绘桶分开；
- age 私钥离线保存，丢了所有备份都解不开；
- `EIDOLON_SECRET_KEY` 和私钥放在一起保存；恢复后没有它，后台 key 解不开、封禁名单对不上。

**手动备份**：

- 后台「立即备份」；或服务器上 `deploy/db-backup.sh`。
- 看后端日志（后台按钮）或 `logs/db-backup.log`（脚本）。
- 退出码见 [`deploy.md`](deploy.md)「备份」的表。

**恢复**：按 [`deploy.md`](deploy.md)「从备份恢复」做。恢复后检查：

- 网站能打开、能登录；
- 后台能进；
- 后台覆盖项没有「覆盖没有生效」；
- 用户、对话、记忆数量正常；
- 备份卡正常。

**演练**：至少每季度在测试环境走一遍恢复，确认私钥能用、步骤没变。

### S8. 升级

1. 读 [`deploy.md`](deploy.md)「升级」，确认这次升级有没有数据库结构变化。
2. 先备份：后台「立即备份」，或 `deploy/db-backup.sh`。
3. 在服务器上：

   ```sh
   git pull
   docker compose -f docker-compose.prod.yml pull
   docker compose -f docker-compose.prod.yml up -d
   ```

4. 跑 doctor：

   ```sh
   docker compose -f docker-compose.prod.yml run --rm backend eidolon doctor
   ```

5. 看后端日志有没有 `WARNING: the admin console's override of …`。
6. 打开后台，检查：
   - 看板数字正常；
   - 配置项没有黄色「覆盖没有生效」；
   - 用户能登录、能发消息、能打电话。
7. 有问题就回滚镜像或按备份恢复。

注意：

- 升级会重启后端，进行中的通话会断开（但会正常结算）。
- 后台覆盖存在数据库里，升级不会丢；但 `EIDOLON_SECRET_KEY` 必须保持同一个。
- 升级后如果某项覆盖试调失败，会回退到 `.env` 并在后台标出来。

### S9. 换服务器

1. 旧服务器先备份：后台「立即备份」或 `deploy/db-backup.sh`；确认存储桶里出现新的一份。
2. 手动带走：
   - `.env`（尤其 `EIDOLON_SECRET_KEY`）；
   - 你额外加的 compose 叠加文件；
   - `deploy/event-names.toml`（如果写了）。
3. 新服务器按 `deploy.md` 部署，恢复数据库，填同样的 `.env`。
4. 如果域名变了：
   - 改 `EIDOLON_DOMAIN`；
   - 更新 GitHub / Google OAuth 的回调地址；
   - 重新申请证书。
5. 切 DNS，验证：
   - 网站、登录、后台；
   - 通话（TURN/coturn）；
   - 备份 cron；
   - 看板。
6. 旧服务器先别删，观察几天。

### S10. 后台进不去

**先分清是哪种**：

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `/admin` 404，设置里也没有「后台」 | 不在 `EIDOLON_ADMINS`；名单为空；没同意条款；被封禁；标识写错；`.env` 没重新读 | 见下面的排查 |
| `/admin` 404，但设置里有「进入后台」 | 前端缓存/旧页面；后端刚重启 | 刷新、重新登录；看后端日志 |
| 能进后台，但某项保存不了 | 试调失败；key 无权限；网络/代理；余额 | 看服务原话；改 key/代理/服务 |
| 某项显示「覆盖没有生效」 | 重启时试调失败；`EIDOLON_SECRET_KEY` 换了；key 被吊销 | 修好覆盖或「恢复成 `.env` 的值」 |
| `.env` 改了不生效 | 这一项被后台覆盖了 | 后台恢复成 `.env` 的值，或改后台 |
| 登录失败 | OAuth 配置错；账号太新/邮箱未验证；被封禁 | 查 `deploy.md`「配置 OAuth 应用」；换账号；解封 |

**排查 `/admin` 404**：

1. 确认你登录的是管理者账号，不是另一个浏览器/另一个 Google 账号。
2. 确认已同意隐私政策和使用条款（没同意时后台也拒绝）。
3. 确认没有被封禁。
4. 在服务器上查标识：

   ```sh
   docker compose -f docker-compose.prod.yml exec backend eidolon user list
   ```

5. 确认 `.env` 里的 `EIDOLON_ADMINS` 和括号里的完全一样（`github:` / `google:` + 数字，不是邮箱）。
6. 确认改了 `.env` 后执行的是 `up -d`，不是 `restart`。
7. 看后端日志有没有配置错误：

   ```sh
   docker compose -f docker-compose.prod.yml logs backend | tail -100
   ```

**后台用不了时**：

- 用户管理仍可用命令行（见 5.8）。
- 配置不能命令行改；如果被错误的覆盖锁住，可以删掉数据库里的覆盖再重启：

  ```sh
  docker compose -f docker-compose.prod.yml exec backend python -c "import os, sqlite3; db = sqlite3.connect(os.environ['EIDOLON_DATABASE_PATH']); db.execute('DELETE FROM config_overrides'); db.commit()"
  docker compose -f docker-compose.prod.yml restart backend
  ```

  **这会撤掉全部后台覆盖**，全部回到 `.env`。做之前先备份。

### S11. 误判补偿（重置卡）

见 6.4。要点：

- 只能全员发，不能定向；
- 发出不能收回；
- 好感度和礼物关着时不能发；
- 发完写公告。

### S12. 用户要求删号

1. 确认对方身份（用他自己登录的账号发来的请求；不要凭邮件地址猜）。
2. 在后台用户详情点「删除这位用户」。
3. 确认框列出的后果，确认。
4. 告诉对方：
   - 线上数据立刻删除；
   - 备份里的副本最多 30 天后消失；
   - 如果之前被封禁，删除后同身份仍然不能登录；
   - 之后再用同一身份登录，会是新用户。

如果对方想保留数据，提醒他先在设置里「导出数据包」，再删除。管理员不能替他导出。

### S13. 新增/移除管理员

**新增**：

1. 让对方先用 Google / GitHub 登录一次，成为用户。
2. 用 `docker compose -f docker-compose.prod.yml exec backend eidolon user list` 找到他的标识。
3. 加进 `.env` 的 `EIDOLON_ADMINS`（逗号分隔）。
4. `docker compose -f docker-compose.prod.yml up -d`。
5. 让对方刷新设置页，确认有「进入后台」。

**移除**：

1. 从 `.env` 的名单里删掉。
2. `up -d`。
3. 对方仍是普通用户，但进不了后台。

注意：

- 所有管理者权限一样，没有「只读管理员」。
- 不要共用管理员账号；出问题无法区分是谁操作的。
- 后台没有审计日志，重要变更自己记一笔。

## 8. 安全与合规

### 8.1 管理员账号

- 后台没有独立密码，安全性等于你的 Google / GitHub 账号。
- 给管理员账号开两步验证；不要用共享邮箱。
- 定期检查 `.env` 的 `EIDOLON_ADMINS`，移除不再需要的人。
- 管理者也是普通用户；不要用管理员账号做日常聊天，减少误操作和暴露。

### 8.2 `EIDOLON_SECRET_KEY`

- 用 `openssl rand -hex 32` 生成，长度和随机性要够。
- **填了就不要再换**。换了的后果：
  - 后台保存的 key 解不开，相关覆盖回退到 `.env`；
  - 封禁名单的哈希对不上，被封禁后删除的人可以重新注册。
- 和 age 私钥一起离线保存；恢复服务器时两样都要有。
- 没有它时，后台的 key 只能看不能改；其他项照常。

### 8.3 备份

- 备份桶必须**私有**，不要和公开的立绘桶共用。
- age 私钥只离线保存，不要放服务器。
- 备份里有用户数据；能读备份的人等于能读数据库。
- 保留期最多 30 天，这是对用户删除承诺的一部分；不要随意调长。
- 定期演练恢复。

### 8.4 不要开开发登录

- `EIDOLON_DEV_LOGIN=1` 让任何人可以冒充任何用户。
- 配置了 `EIDOLON_DOMAIN` 的公开部署会拒绝启动；不要试图绕过。
- 本机开发用完就关。

### 8.5 数据可见性

- 后台界面和 API 不提供用户对话、记忆、档案、好感度、礼物等；这是产品承诺。唯一的例外是「增加抽奖次数」：可以给某位用户加次数，但仍然看不到他现有的次数和礼物。
- 服务器 root 仍可直接读数据库；管理纪律是不要翻。
- 运行记录保留 90 天，不含对话内容；备份里有，所以加密。
- 删除用户后，运行记录不再关联到人，但全站统计不变。

### 8.6 公开部署的合规提醒

- 语音识别用阿里云百炼北京地域时，陌生用户的声音会送到中国内地处理并按中国法律保存；隐私政策已写明。
- 向量化用 Gemini 时，服务器要在开放地区；公开部署应开计费并设 `GEMINI_BILLING_ENABLED=1`。
- 生图（NovelAI 官方 token）对公众开放有条款风险；中转可能被封。
- 你是部署者，对内容、费用、数据处理和当地法律负责；使用条款和隐私政策要如实填写 `EIDOLON_CONTACT`。

## 9. 故障排查

| 现象 | 先查 | 处理 |
|---|---|---|
| `/admin` 404 | 是否管理者、是否同意条款、是否被封禁、名单是否为空、标识是否写错、是否 `up -d` | 按 S10 排查；用命令行管用户 |
| 登录页显示「部署者还没有配置登录方式」，也没有「开发登录」 | 后端没加载 `.env`；`/api/auth/providers` 返回 `dev_login:false` | 按附录 A 用 `uv run --env-file=../.env` 启动后端 |
| 设置里没有「进入后台」 | 同上 | 同上 |
| 保存配置失败 | 服务返回的原话 | key/余额/权限/地址/代理；修好再存 |
| 某项「覆盖没有生效」 | 后台显示的失败原因；后端启动日志 | 修好覆盖，或「恢复成 `.env` 的值」 |
| 改了 `.env` 不生效 | 是否被后台覆盖 | 后台恢复，或改后台 |
| 用户 429 | 限额 | 调高全站限额、给该用户单独放宽，或让用户等恢复时间 |
| 用户 503 | 同时通话满了 | 调高 `concurrent_calls`，或排查异常长通话 |
| 邀请链接无效 | 是否过期/用完/被删；注册方式；是不是第一个用户 | 重新生成；确认模式；第一个用户不用邀请 |
| 公告用户看不到 | 是否发布；是否撤回；是否草稿 | 发布；让用户刷新/看铃铛 |
| 备份异常 | 备份卡、`logs/db-backup.log`、后端日志 | 按退出码处理；检查 cron/桶/密钥 |
| 看板花费为 0 或偏低 | 有没有设单价；是不是自带密钥 | 「单价」里补；自带密钥只列用量 |
| 服务状态一直红 | 服务健康错误类别 | key/余额/网络/代理 |
| 看板数字不更新 | 页面是否可见；数据截至时间 | 手动刷新；看后端日志 |
| 赞赏上传失败 | 格式/大小 | PNG/JPEG/WebP，≤2 MB |
| 单价改了但合计没变 | 有没有生效单价；币种 | 看「生效单价」；按币种分别汇总 |
| 通话/对话页没有立绘，衣装面板或缩略图是空的 | 8765 是否在监听；静态服务的根目录是不是 `corpus/stand`；前端 CSP 是否允许 8765 | 按附录 A.2 启动静态服务；前端带 `EIDOLON_STAND_ASSETS_URL` 重启 |
| 后台页面报错/空白 | 浏览器缓存、后端日志 | 刷新/重新登录；看日志 |

**通用排障顺序**：

1. 看后台「服务健康」和「备份」；
2. 看后端日志：

   ```sh
   docker compose -f docker-compose.prod.yml logs backend | tail -200
   ```

3. 跑 doctor（只查 `.env`）：

   ```sh
   docker compose -f docker-compose.prod.yml run --rm backend eidolon doctor
   ```

4. 确认 `.env` 和后台覆盖的关系；
5. 需要时回滚配置或恢复备份。

## 附录 A：本机直接跑（非 Docker）

正文按 `docker-compose.prod.yml` 写。自己电脑上直接跑（uv + Node.js）时，启动方式不同；下面这套能避免「登录页没有开发登录」和「前端看不到新功能」。

### A.1 后端

在仓库根目录：

```powershell
cd backend
uv run --env-file=../.env eidolon serve
```

- 必须带 `--env-file=../.env`。`uv` 会把 `.env` 读进后端进程。
- **不要**用 `.\.venv\Scripts\eidolon.exe serve`：它不会读 `.env`。结果就是 `/api/auth/providers` 返回 `dev_login:false`，登录页显示「部署者还没有配置登录方式」，`/admin` 也 404。
- 没有 `uv` 时先装：`winget install --id astral-sh.uv -e`，装完重开终端。
- 改了 `.env` 后要重启这个命令，`restart` 不适用于直接跑。

启动后确认：

```powershell
curl.exe http://127.0.0.1:8000/api/auth/providers
```

本地开发应该看到：

```json
{"providers":[],"dev_login":true,"contact":null}
```

`providers` 为空是正常的：本地没配 GitHub/Google OAuth，用下面的「开发登录」即可。

### A.2 立绘静态服务（要看通话立绘和衣装时）

立绘、衣装清单和缩略图在本机的 `corpus/stand/` 下，需要一个静态服务器把它们提供给浏览器。本机辅助脚本在 `D:\lzh\github\tools\static-server.js`（不在仓库里）；它支持以 `corpus/stand` 为根，并在找不到时回退到 `source/assets`，所以衣装清单、缩略图和 spine 都能加载。**根目录要传 `corpus/stand`**：

```powershell
cd D:\lzh\github\eidolon-sc
node ..\tools\static-server.js corpus\stand 8765
```

没有这个辅助脚本时，仓库文档里的简单办法是 `npx http-server corpus/stand/source/assets -p 8765 --cors`；它只能提供 spine，衣装清单和缩略图会 404，换衣装面板就用不了。

然后确认 `.env` 里有：

```sh
EIDOLON_STAND_ASSETS_URL=http://localhost:8765
```

验证：

```powershell
curl.exe http://localhost:8765/outfits/1.json
curl.exe http://localhost:8765/spine/idols/stand/1030010010/data.json
curl.exe http://localhost:8765/thumbnails/stand/1030010010.png
```

三个都返回 200，才说明立绘、衣装清单和缩略图都能拿到。

常见错误：

- 把根目录写成 `corpus/stand/source/assets`：`/spine/...` 能开，但 `/outfits/...` 和 `/thumbnails/...` 会 404，衣装面板和立绘都会缺东西。
- 只启动前端、不启动 8765：页面能开，但通话层没有立绘。
- 8765 已经在跑别的静态服务：先结束它，再用 `tools/static-server.js` 以 `corpus/stand` 为根启动。
- 前端启动时没带 `EIDOLON_STAND_ASSETS_URL`：CSP 会挡掉 `http://localhost:8765`，浏览器控制台会报 CSP 错误。

### A.3 前端

第一次先装依赖：

```powershell
cd frontend
npm ci
```

每次改完前端代码：

```powershell
npm run build

Copy-Item .next\static .next\standalone\.next\static -Recurse -Force
if (Test-Path public) {
  Copy-Item public .next\standalone\public -Recurse -Force
}

$env:HOSTNAME = "127.0.0.1"     # 手机/局域网访问改成 0.0.0.0
$env:PORT = "3000"
$env:BACKEND_URL = "http://localhost:8000"
$env:EIDOLON_STAND_ASSETS_URL = "http://localhost:8765"   # 不看立绘可以省略
node .next\standalone\server.js
```

- 这个项目是 Next.js `output: standalone`。`npm run start` 会提示 `"next start" does not work with "output: standalone"`，不要用它。
- `.next/static` 和 `public` 不会自动进 `.next/standalone`，要像上面这样复制；不复制的话页面能开，但 JS/CSS/图片会 404。
- 改完前端要重新 `npm run build` 并重启 `node`，浏览器再硬刷新（`Ctrl+F5`）。只重启不 build 还是旧界面。

端口被占用时，先结束占用 3000 的进程：

```powershell
Get-NetTCPConnection -LocalPort 3000 -State Listen
Stop-Process -Id <上面查到的 OwningProcess>
```

### A.4 本机登录与管理者

本机 `.env` 推荐：

```sh
EIDOLON_DEV_LOGIN=1
EIDOLON_ADMINS=
```

这样登录页有「开发登录」，填一个名字就能进；没设管理者名单时，开发登录的用户都是管理者，`/admin` 能进。

注意：

- 如果 `EIDOLON_ADMINS` 填了名单，**名单优先**：开发登录建出来的用户没有 GitHub/Google 身份，不会自动成为管理者。本机自用就保持名单为空；要指定管理者就配 OAuth，把 `github:...` / `google:...` 填进名单。
- `EIDOLON_DEV_LOGIN=1` 不能和 `EIDOLON_DOMAIN` 一起用；公开部署必须删掉开发登录。
- 生产环境不要用开发登录，按正文第 2 节配 OAuth 和管理者名单。

### A.5 启动顺序

1. 先启动后端，确认 8000 在监听、`/api/auth/providers` 正常；
2. 要看立绘时，启动 8765 的静态服务；
3. 再启动前端，确认 3000 在监听，并带上 `EIDOLON_STAND_ASSETS_URL`；
4. 打开 `http://127.0.0.1:3000`，登录后进 `/admin`。

这些进程都要一直开着。关掉终端或结束进程，服务就停了。
