# 管理者可以给一位用户增加抽奖次数

原先抽奖次数只能由系统发：每天两次、成就阶段、酒吧当天的第一次光顾，加上偶尔的重置卡；管理者只能在配置页给所有现有用户各发一张重置卡，不能单独给某位用户任何东西（ADR-0025）。实际运营里，判断模型误判、活动补偿、故障道歉都需要比「全员重置卡」更细的补偿，而直接改数据库会绕过应用的事务、用户删除和礼物开关。

现在用户详情页多一个「增加抽奖次数」：管理者填 1 到 1000 次，次数加在这位用户现有的抽奖次数上，可以超过每天最多攒的 7 次；好感度和礼物关着时不能加。增加记成一次奖励（`gift_rewards` 里的一行，键带一次性前缀），所以用户下次打开礼物页会看到「新到的抽奖次数」，和成就到账一样。后台仍然不显示用户现有的抽奖次数、礼物和好感度，也不提供「把次数设成多少」；只能加，不能撤回。

## Considered Options

- **只给全员发重置卡**：不破坏原设计，但补偿不到具体某个人；误判只影响一位用户时，其他人平白多一张卡。
- **允许直接设用户的抽奖次数**：更灵活，但会暴露余额，也能把次数改小，等于把运营工具变成惩罚工具；不采用。
- **在数据库里手工改**：不用改代码，但绕过事务、礼物开关和用户删除，容易留下孤儿行；不采用。

## Consequences

- 抽奖次数不再完全「只能在本部署里挣来」：管理者可以补偿，但数据包仍然不带它，导入后从零开始（ADR-0025 的修订）。
- 增加没有单独的审计表；`gift_rewards` 只记发放键、次数和时间，不记哪位管理者发的。需要留痕的部署自己记录。
- 用户删除时，`gift_balances` 和这次奖励的 `gift_rewards` 行一起删除；后台的「增加抽奖次数」也因此没有历史可查。
- 礼物、好感度、成就、日程、酒吧和数据包的规则不变；管理者仍然不能单独发礼物，好感度仍然只有重置卡能改。
